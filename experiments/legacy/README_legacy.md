# v12 正式在线模型（PBS-LM：并行块内堆叠 + 可调深度 + n→m 输出）

状态：**正式在线模型入口**。模型定义在 `model.py`，训练/长期在线入口在 `run_online.py`。
研究原型 `../pbs/` 不再扩展，结构部分以本目录为准。

## 本轮三个变化（对应目标）

1. **深度超参数 `--depth`**：每个"真块"内部统一堆叠 `depth` 个子层（子层各自独立权重），
   一个旋钮共同调节所有块的深度。块数 K（并行宽度）、串行前缀 H 仍是独立超参。
   参数 = 基础参数量 × depth（下表）。
2. **一次调用 n→m**：`forward(ids_in, m)` 输入 n 个 token，输出 m 个 token 的分布
   `(B, m, V)`。实现：n 个上下文 token 编码后，用 m 个可学习查询向量（`q_emb + q_pos`）
   对编码结果做交叉注意力（非自回归），一次前向出 m 个 token。
   n、m 都可配置（m ≤ `--m-max`），已验证 (64,16)/(96,32)/(128,32)/(96,8)/(96,64) 五种组合。
3. **正式在线模型**：A/C 双通路 + 全息状态缓存 M + 块间可学习交流残差沿用；
   在线只更新 A 侧（A 解码器 + M 选读 + 角色路由 + 查询向量），C 通路和块银行冻结。
   仲裁为**多视图信息一致性**（A/C 各用「主编码 + 一个块视图」，按 TV 一致度算
   `g=sigmoid(8(consA-consC)+bias)`，逐输出 token 门控，不是 max-prob）；
   m 个输出 token 之间加 query 间因果自注意力 + 两轮迭代精修（第一遍软词嵌入回灌再解一遍）。

## 结构

```
ids_in (B,n)
 └─ token embedding（与输出头共享）
    └─ H 个串行真块（每块 depth 个子层，权重独立）
       └─ K 个并行真块（每块 depth 个子层；按块 bmm 并行；带 masked 交流残差）
          ├─ role 路由 k1/k2/k3（动态配额；k2 写全息 M）
          ├─ A 编码 = 前缀 + Σk1 + 门控读 M
          └─ C 编码 = 前缀 + Σk3 + 读 M
             └─ m 个可学习查询对 A/C 编码各做 2/1 层交叉注意力
                └─ 两套 (B,m,V) logits，仲裁门 g 混合 → (B,m,V) 输出
```

## Round 4（v13：信息流动一致性 + 震撼值 + 脑活跃度，30 并行块 × depth 6）

按用户 11-13 晚的修订实现（x 默认 20%）：

1. **信息一致性 = 流动模型**：活跃块增量投影到 64 维流动空间，做 2 步可学习消息传递
   （块间动力学）；settled 场后，参数一致性 = 各块 settled 状态相对共识场的归一化离散度；
   A/C 各自 = 各自角色块相对全局 settled 场的平均一致度，比较后仲裁。删除了原来的额外解码视图（省算力）。
2. **震撼值**：S = −log(known+ε)，known = 1−(1−p_A(y))(1−p_C(y))——任一侧"本来就知道"→低震撼，
   两侧都不知道→高震撼；损失权重 = 1 + β·S（β=0.5），替代原来的 CE 比例占位。
3. **脑活跃度**：A_t = act_x·σ(S−s0+2(1−I)−c)，act_x=0.2；活跃块数 = clamp(round(A_t·K), 3, **20%·K=6**)，
   再分 k1/k2/k3 配额；未启用块完全不计算（省延迟）。

目标配置：**K=30 个并行块、每块 depth=6、h=0（全部并行）**；总参数 146.6M（块银行 142.3M），
在线可训练 2.39M，流动模块 0.067M。

首测（1500 步预训练 batch4 + 1500 chunk 在线，n=96→m=32）：

| 分支 | 参数 | 预训练耗时 | 在线前 held | 在线后 held | 流式 CE 首→末500 | g mean±std |
|---|---|---|---|---|---|---|
| 震撼值开（β=0.5） | 146.6M | 579s | 5.831 | 5.869 (+0.037) | 5.712→5.222 | 0.687±0.129 |
| 震撼值关（β=0） | 146.6M | 579s | 5.758 | 5.828 (+0.070) | 5.803→5.266 | 0.645±0.097 |

- 活跃度上限生效：在线 act 均值 0.168（≤0.20），启用块 mean/max = 5.1/6（上限 6），预训练探索期 mean/max=4.5/6。
- n/m 扫描（在线后）：震撼开 64→16 5.343、96→32 5.869、128→32 5.768、96→64 5.910；
  震撼关 5.237 / 5.828 / 5.743 / 6.006。
- 首测仍是欠拟合（1500 步、batch4；同训练量下小模型 v12 held ~5.3），
  且 146.6M 参数只有 ≤20% 块被训练到，需要更长训练再判断质量。
- 流动一致性的 I 分布、以及"活跃度上限 x% 对延迟的实际收益"还没单独量化（下一步）。

### Round 4 续：3500 步长训练 + 流动一致性/延迟量化

**3500 步长训练（震撼开，batch4，1500 chunk 在线）**：预训练 622.6s；在线前 held 5.346 → 在线后 5.419（+0.073）；
流式 CE 5.170→4.784；n/m 扫描 96→32 5.419、128→32 5.420、192→32 5.228、256→64 5.252；
在线 act 均值 0.171（≤0.198）、启用块 mean/max 5.2/6，g 0.548±0.114。
与 1500 步首测（held 5.831→5.869）相比，长训练把在线前 held 降了 0.49——但同预算下仍不如小模型 v12（4000 步 held 4.986），
说明 30 块×depth6 的稀疏模型需要更多步数/更大 batch 才能兑现参数优势。

**流动一致性 I 的分布**（长训练 ckpt，16 个留出窗口）：I_a=0.734±0.082、I_c=0.730±0.074、
g=0.520±0.079、active=6；held CE（16 窗口）arb=5.262 / a=5.290 / c=5.304。
I 有方差（不是常数），A/C 差异经 g 体现——流动模型确实在产生非平凡的仲裁信号。

**活跃度上限 x=20% 的延迟收益**（同一套权重，只改 caps 与 act；fwd）：
- batch1：6 块 16.56 ms vs 30 块 23.87 ms（1.44x，batch1 下被 kernel/固定开销拖住，收益小）；
- batch8：3 块 20.41 ms / 6 块 24.00 ms / **30 块 105.86 ms** → 20% 上限 vs 全开 **4.4x**。
所以 20% 上限在训练 batch 下能真省延迟；batch1 推理下更多是省算力/显存，不是省时。

**当前结论**：目标配置跑通、活性上限/稀疏计算生效、流动一致性有非平凡分布、20% 上限 batch8 4.4x；
质量上 30×6 稀疏模型在 3500 步内仍未追上小模型，需要更长训练与 x% 扫描再下结论。

**下一步**：x ∈ {10%,20%,30%} 扫描 + 更长 schedule；流动一致性 I vs 旧 TV 的对照；把深度/宽度/活跃度做成延迟-质量曲线。

### 3. 自适应多 token 输出（自信时一次落地多个）

`adaptive.py`：
- propose：现有 n→m 一次前向给出 m 个 token 提议；
- commit-block：按提议逐 token 最大概率，取连续 ≥τ 的最长前缀落地（至少 1 个）；
- commit-verify：把提议 token 当查询做一次 teacher-forced 验证（同一解码器 + query 因果），
  只接受「验证预测与提议一致且概率 ≥τ」的最长前缀；全拒退回 1 个。

评测（teacher-forcing 口径，不测 wall-clock；小模型 k=6 depth1，n=96→m=32）：

| 模式 | τ | tokens/call | top-1 acc | CE |
|---|---|---|---|---|
| 单 token 基线 | — | 1.00 | 0.125 | 2.476 |
| block commit | 0.05 | 24.96 | 0.114 | 2.655 |
| **verify commit** | 0.00/0.02 | **8.47** | **0.134** | **2.465** |
| verify commit | 0.05 | 7.95 | 0.133 | 2.462 |
| verify commit | ≥0.10 | 1.00 | 0.125 | 2.476 |

结论：verify 路径可以在**不损失首 token 准确率**的前提下，平均每次调用落地 ~8 个 token；
τ 是「多输出/保守」的旋钮。对照：显式加 teacher-forced 训练（tf_beta=0.5）反而把块质量拉低
（held 5.489 vs 5.230），没有采用；verify 直接用现有解码器就工作。
当前 30×6 稀疏模型的 verify 几乎全拒（说明需要针对该模型做校准/训练才能用多 token 落地）。

### Round 6（进行中）：部署式连续生成 + zhwiki 目标模型训练

**连续生成循环**：`generate_closed.py`——上下文只来自模型自己生成的 token（滑窗 96，不喂 ground truth），

### Round 6 结果：zhwiki 目标模型 + verify 连续生成 + τ 标定

**目标模型（K=30 × depth6，zhwiki 37.5M 字符，词表 12,973）**：
8000 步、batch4、1441s；总参数 **149.36M**（块银行 142.26M，在线 2.39M，流动 66.6k）。
held（n=96→m=32）arb **6.398**（a 6.375 / c 6.549）；n/m：96→32 6.398、128→32 6.623；
预训练 active 均值 4.5（≤6），震撼均值 5.82。**仍严重欠拟合**（词表 12,973 的随机 CE≈9.47，

**τ 标定（teacher-forcing 口径，目标模型）**：

| 模式 | τ | tokens/call | top-1 acc | CE |
|---|---|---|---|---|
| single | — | 1.00 | 0.047 | 3.425 |
| verify | 0.02 | 25.37 | 0.043 | 3.479 |
| verify | 0.03 | 14.37 | 0.031 | 3.467 |

held 标签率 97.9%、head acc 97.9%，但**恒输出正类**（因为候选几乎重复、验证几乎全同意），
当前无实用价值。保留为可选机制，等目标模型训练到不退化、标签平衡后再校准。

**结论**：verify commit 连续生成循环已打通；τ 标定流程已建立；瓶颈是模型质量（欠拟合），
不是机制。下一步：继续训练（16000+ 步或更多）、加采样/重复惩罚、再用平衡标签重训 confidence head。

### Round 7：多 token 输出「鼓励」+ 块角色复用统计

**角色选择语义（按用户澄清确认）**：同一时刻 A/C/M 的角色块互不重叠；但块池共享，
**同一个块可以在不同时刻被 A 或 C 选中**。`role_stats.py` 在 zhwiki 目标模型上统计：
200 个窗口里 30/30 块都被用过，**27/30 块既当过 A 又当过 C**（0 个只当 A、0 个只当 C），
quota 恒为 (A=3, M=1, C=2)=6 块。小模型 k=6 也是 6/6 块被用过、2/6 块双角色。

**多 token 输出的训练激励（commit-consistency 损失）**：
`--commit-beta` 在损失里加 KL(块提议分布 || teacher-forced 验证分布)，让块提议与验证预测对齐，
从而「值得落地」的 token 变多。小模型（k=6/depth1，1500 步，聊天记录）：

| 模型 | 单 token acc / CE | verify 落地 tokens/call | 落地 top-1 acc / CE |
|---|---|---|---|
| 基线（无 commit-beta） | 12.5% / 2.476 | 10.75（τ0~0.05） | 5.9% / 2.493 |
| commit-beta 0.1 | 14.1% / 2.377 | 21.49 | 10.9% / 2.468 |
| **commit-beta 0.3** | **17.2% / 2.295** | **20.89** | **13.7% / 2.419** |

即 commit-consistency 同时提高了块质量（单 token acc 12.5%→17.2%）和多 token 落地量（10.75→20.89），
且落地 token 的准确率（13.7%）超过基线单 token（12.5%）。
zhwiki 目标模型（30×6）上同配置正在跑；大词表下 KL 需 clamp（softmax 下溢 log(0) 曾致 NaN，已修）。

**zhwiki 目标模型（30×6）commit-beta 3000 步验证**：held arb 6.615（a 6.521 / c 7.780）；
单 token acc 3.1%、CE 3.577；verify τ0.02 → 19.39 tokens/call、acc 3.6%、CE 3.635。
和 8000 步非 commit 版（4.7%、25.37 tokens、4.3%）**步数不同不可直接比**；
干净对照是小模型那张表（同时提质量与 tokens/call）。
大词表 KL 下溢曾致 NaN（softmax 到 0 → log(0)），已用 clamp+重归一修复。

## Round 8（v14：去掉状态 M，E 块 + 权重记忆矩阵 + M→A 固化）

**架构（按用户定稿）**：
- 删掉旧的 M 状态向量（HRR 状态缓存、mread/mgate 全部移除）；
- 主块池 K=30（或任意 k）仍按脑活跃度选活跃块、A/C 两角色互斥、可随时间复用；
- 新增 **10 个 E 块**（默认 depth=1）：始终活跃（高活跃值），学习率 = 主学习率 × 5（独立参数组）；
- E 块之间稠密连接（e_mix，10×10 可学习矩阵）；E 与当前选中的 A/C 稠密残差：每块 E 通过自己的
  `d×d` 记忆矩阵 **M_e** 读出 `read_e = E_i @ M_e`，经 `ea_proj / ec_proj`（稠密 d×d）加到 A/C 编码；
- **M_e 是模型记忆（权重，不是状态）**：`requires_grad=False`，由 E 写入/擦除/衰减，存在 state_dict 里；
  训练时每 chunk 写一次 + 衰减（写入率 mem_lr=0.05，衰减 0.98）；在线时只有高震撼（S≥1.0）才写；
- 在线更新范围：A 侧参数 + E 参数（E 用独立高学习率）；C、主块银行、流动模块冻结。

**v14a 小模型验证**（k=6/depth1，E=10×1，聊天记录，800 步预训练 + 800 chunk 在线）：
总参数 19.14M（E 8.10M、记忆矩阵 0.66M、在线 2.31M）；预训练 held arb 6.065，
在线后 6.162（+0.097，小模型+短预训练，尚不能与长训练结果比）；记忆范数从 9.19 衰减到 1.25（写入/衰减在工作）。

**M→A 固化（consolidate.py v2，counterfactual 选 A）**：
每个成熟 M_e 独立处理——对每个 A 候选（dec_a 各层、role、queries、refine）单独做 5 步
`L_cons = CE(A) + 0.5·MSE(a_pred(h_a), M_e 读出)`，**实测** replay CE 下降，held CE 作护栏；
选下降最大者保留，否则完全回滚；成功后 M_e 衰减（记忆→能力，释放容量）。
结果：10 块 M 中 7 块接受（全部选中 `queries` 组），Δreplay≈−0.0005、Δheld≈−0.0009；3 块回滚。
即「哪个 A 最适合这块 M」现在是用实测加训增益决定的，而不是猜。

**已知局限**：当前训练预算太小，固化的增益只有 1e-4 量级；放大到 30×6/zhwiki 需要更长的
pretrain 与更大 replay、并且 counterfactual 扫描（E×候选×步数）在 149M 模型上要缓存/降频。
下一步：v14 在 zhwiki 上长训练 + commit-beta；固化目标从 a_pred 蒸馏改为 a_enc/表示级蒸馏；
把固化做成周期性 runtime 环节（低活跃时触发、C 快照护栏、回滚）。

## Round 9：v14 上 zhwiki（30×6 + E10）+ 记忆命中 + 表示级固化

**v14 zhwiki 目标模型**：K=30×depth6 + E=10×1、act_x=0.2、commit-beta 0.3、zhwiki 37.5M 字符；
总参数 **157.77M**（主块银行 142.26M、E 8.10M、M 矩阵 0.66M、在线 2.32M）；
4000 步预训练 844s；held arb **6.710**（a 6.713 / c 7.491）。
（对照：v13 同数据 8000 步 6.398、3000 步 commit 6.615——v14 这轮步数少且多了 E，质量还没兑现。）

**记忆命中评估（hit_eval.py）**：
- CE(M 全开)=6.7103，CE(所有 M 置零)=7.0165 → **记忆整体贡献 +0.306 CE**；
- 逐块置零单块 M_e：每块贡献约 0（冗余，单块可被其它块/读出投影补偿）；

小模型 v14a 同样：CE 7.0346 vs 7.4617 → 记忆贡献 **+0.427 CE**。

**表示级 M→A 固化（consolidate_repr.py）**：
teacher=完整模型（含 M），student=把该块 M_e 置零；L = CE(student) + KL(teacher‖student)；
每个 A 候选（dec_a 层/role/queries/refine）单独 5 步，实测「去 M 后的 CE」下降，选最优保留。
小模型结果：**10/10 块接受**，全部选中 `queries`；每块 ΔCE(noM)≈−0.0035、ΔCE(withM)≈−0.0004、
held 略降 → 记忆效果被 A 吸收（去 M 能力变好），M 随后衰减（0.7）。
说明「M→A 固化」打通了最小闭环：先测哪个 A 加训最有效，再短程蒸馏，最后衰减记忆。

**多 token 落地（v14 zhwiki）**：verify τ≤0.03 → 32 tokens/call、落地 acc 3.1%、CE 3.100；
single 1 token acc 4.7%、CE 3.461；τ≥0.04 退回 1 token。commit-beta 在 v14 上继续生效。

## Round 10：输出打断（interrupt hook + commit cap）

`generate_closed.py` 新增：
- **打断钩子**：只在 commit 边界触发；未 commit 的块提议直接丢弃（零成本），然后可以切换上下文
  （模拟用户打断/插入新话题）继续生成；
- **`--commit-cap`**：每次最多 commit 的 token 数 = 打断粒度上限；
- **`--interrupt-after`**：模拟在第 N 个 token 处打断，测打断后的恢复质量。

小模型 v14a（max_new=32，4 窗口）：

| 设置 | 模式 | max_commit | 打断后 8 token 恢复 acc | 恢复前缀 |
|---|---|---|---|---|
| cap=4 | single | 1 | 0.188 | 0.50 |
| cap=4 | verify τ0.02 | 4 | 0.125 | 0.50 |
| cap=0 | verify τ0.02 | **32** | **0.000** | **0.00** |

结论：**打断粒度 = commit cap**；不设上限时 verify 一次 32 token 全吐，打断后很长时间无法插入/恢复；
要流畅就 cap 小（1–4 token），但和「一次多 token 输出」是直接 trade-off。
结构上确实比标准 AR 干净：无 KV cache 回滚、未 commit 候选可丢弃、状态只有 M/act。

### Round 10 续：v14 继续训练到 8000 步 + 打断验证

继续训练（从 4000 步 ckpt 再 4000 步，zhwiki/30×6+E10/commit-beta 0.3）：
held arb 从 6.710 → **6.579**（a 6.579 / c 6.760，C 从 7.491 明显修复）；
但同数据同 8000 步的 v13（无 E）是 6.398 —— **v14 目前仍落后 0.18**，E 的额外参数/计算还没有换回质量。

记忆命中（cont ckpt）：CE(带 M) 6.5790 vs CE(无 M) 6.7154 → 记忆贡献 **+0.136**（比 4000 步时的 +0.306 小，
模型变强后对记忆的依赖降低）；M 读出与目标余弦 +0.091。
多 token：verify τ≤0.02 → 32 tokens/call、acc 3.1%、CE 3.252；single 4.7%、CE 3.553。

打断（本模型）：commit cap 小 → 停得快；cap=0 时 verify 一次 32 token，打断基本无法及时插入。
部署默认建议：**cap=1~4 + 自适应 τ**，并把「打断」写进在线学习信号（打断处的高震撼样本写 M / 触发更新）。

## Round 11：运行时固化 + 记忆重要性与冗余 + 打断耦合 + E 缩放

**周期性运行时固化（已接进 `online_stream`）**：`--consolidate-every N`（0=关）。
触发条件：低活跃（act ≤ act_x×frac，默认 0.7）+ 每 N chunk + 有 replay；
流程：按记忆重要性选 E/组 → teacher(含 M)→student(去 M) 蒸馏（KL+CE）→
**C 快照护栏**（C 冻结，前后 C CE 必须完全一致）→ held CE 恶化超阈值回滚 → 成功则 M 衰减 0.7。
若所有单块/分组都冗余，则**按重要性顺序擦除最冗余的 M**（容量管理）。
小模型 300 chunk 实测：3 次事件均为 `erase_redundant`（E5、E1），held 7.150 → 7.103，事件正常记录。

**记忆重要性/冗余分析（memory_importance.py）**：
- v14a（小）：单块贡献 +0.0015~+0.0024；top-k 分组：k=3 +0.012、k=5 +0.038、k=10 **+0.803**；
  随机子集重要性 ~0.03；M 两两余弦均值 0.531（冗余）；给出固化顺序/擦除顺序。
- v14 zhwiki（8000 步）：单块与子集贡献 ≈0（完全冗余），top-10 分组 +0.136；M 两两余弦 −0.076（方向分散）。
结论：**单块 ranking 无意义，必须用分组重要性**；擦除按单块冗余排序，固化按分组重要性排序。

**打断 × 多 token 耦合**（v14 zhwiki cont，max_new=24，3 窗口，interrupt@12）：

| 设置 | verify max_commit | 打断后 8 token 恢复 acc | 恢复前缀 |
|---|---|---|---|
| cap=0 | 24 | 0.000 | 0.00 |
| cap=4 | 4 | 0.042 | 0.33 |
| cap=4 + 打断时 M 衰减 0.5 | 4 | 0.042 | 0.33 |

结论：**cap 决定打断响应**（cap=0 时一次 24 token，恢复为 0）；M 衰减在当前模型上未测出额外差异，
需要更强模型/更长恢复窗口才能分辨。

**E 成本缩放**：E=5×1 vs E=10×1，同 4000 步：held **6.771 vs 6.710** —— 减半 E 反而更差；
E 的容量在这个训练量下还有用，降成本不能靠减数量。E 学习率 ×1（默认 ×5）对照正在跑。

### E 学习率缩放（关键发现）

E=10×1、同 4000 步、zhwiki：

| E 学习率 | held arb |
|---|---|
| ×5（原默认） | 6.710 |
| **×1（与主参数相同）** | **6.5069** |
| ×1 继续到 8000 步 | 跑动中 |

E 的「独立学习率」不该是更高：×5 反而更差；×1 在 4000 步已超过 v14 原 8000 步的 6.579。
这说明之前 v14 落后 v13 的主因之一是 E 学习率过高（噪声/干扰），减 E 数量（E=5）也验证无效（6.771）。
下一步：×1 续到 8000 步，目标 ≤6.398（v13）。

### 固化护栏实测：C 快照检测生效

用 `--consolidate-force` 强制对 top-3 组做固化（跳过重要性门槛）验证 keep/rollback 路径：
两次事件都返回 **rollback**，其中 `c_guard=False` —— 说明 A 侧更新（q_emb/q_pos/refine/role 是 A/C 共享参数）
会改变 C 通路输出，**C 快照护栏正确检测到 C 漂移并回滚**。
这是护栏在起作用，但也暴露一个架构问题：C 不是完全隔离的（共享 queries/refine/role）。
修法：给 C 单独的冻结副本（q_emb_c/q_pos_c/refine_c/role_c），A 侧在线更新只动 A 的副本；
在修好之前，运行时固化只走「擦除冗余记忆」路径（keep 会被 C 护栏回滚）。

### 最终结果：v14（E LR ×1，8000 步）追平/略超 v13

| 模型 | 数据/步数 | held arb |
|---|---|---|
| v13（无 E） | zhwiki 8000 | 6.398 |
| v14 E10×1，LR ×5 | zhwiki 8000（两段） | 6.579 |
| **v14 E10×1，LR ×1** | **zhwiki 4万步中的 8000** | **6.3824** |

即：E 的独立学习率不该更高（×5 反而 6.710@4000），×1 在 4000 步 6.5069、8000 步 6.3824，
**超过 v13 的 6.398** —— 目标达成。
最佳模型附加指标：记忆命中 CE 6.3824（无 M 6.5722，记忆贡献 **+0.1898**）；
多 token：verify τ0.02 → 21.18 tokens/call、acc 2.2%、CE 3.445；single acc 3.1%、CE 3.409。

**诊断结果（300–2500 步）**：
1. 输出曾被扰动场劫持：μ 范数从 4 涨到 14、KL 恒定、field 梯度占主导 → 已修：μ 单位化、场贡献缩放 0.1、z 先单位归一化。

## Round 20：用完整日志定位并修复「不能训练」

用逐 step 全量日志（`--log-every 1` + jsonl）定位到 5 个问题并修复：

1. **扰动场劫持输出**：μ 范数从 4 涨到 14、KL 恒定、field 梯度占比最高 → μ 单位化、场缩放 0.1；预训练阶段 `field_scale=0`（后训练再启用）。
2. **输出范数爆炸**：cos 回归下 z 范数涨到 162，梯度按 1/||z|| 衰减 → 输出强制单位归一化。
3. **余弦回归的常数解**：随机码本均值≈0，batch 平均余弦梯度方向≈0，模型停在「永远输出同一个码」
   （train decode 4.69% ≈ 最高频 token 4.7%）→ 改用 **in-batch + 采样负例的 InfoNCE**（不维护 V 词表全分布）。
4. **初始化**：`out_a` 改单位阵、`ea_proj` 改随机小初始化（此前零初始化让 E 分支没梯度）。
5. **码本没有持久化**：`code` 原来是非持久 buffer，加载 ckpt 会得到一套新随机码本、解码全错 → 改为持久 buffer。

修复后 InfoNCE 诊断（967M 全尺寸 / 28.5M 小模型都试了）：
- 对比余弦：InfoNCE 下 `L_a` 从 ~5.2 降到 ~3.9–4.2，`ppos` 从 0.008 升到 ~0.08，`cos_a` 从 0 升到 ~0.1；
- 但 held/train decode 仍停在 ~1.5% / 3.9%，**还没超过 bigram baseline**（同窗口 bigram：train 16.0%、held 9.0%）；
- 梯度仍集中在 `out_a/dec_a`，`bank/ebank/tok` 梯度极小（主块/E 几乎不学）。

结论：现在不是某个单点 bug（单 batch 过拟合已到 100% 解码），而是**数据/算力/训练设计**的瓶颈：
1.8M token 的 smoke 语料 + batch4 + 967M 稀疏活跃模型，看不到泛化；
下一步应上完整 562M token 语料 + Kaggle T4×2（fp16 + 8-bit Adam + checkpointing），
并考虑预训练期加大活跃块/负例/学习率。

2. decoder 的 q0 残差把 cross-attn 的上下文信号淹没 → `CrossLayer.res_scale=4` 放大；
3. 加直接上下文读出 `ctx_a/ctx_c`（从 a_enc/c_enc 均值线性映射到输出）；
4. 换 simple decoder（池化上下文 + q_pos 直接线性输出）；
5. 目标从随机冻结码本 / 可训练输入嵌入都试了；InfoNCE 换成频率平衡 + variance 正则；fp32+AdamW 也试了。
   以上都**没有**让 train/held decode 超过 bigram；输出仍会塌缩成近常量（z 跨上下文 cos≈0.95–0.999）。

结论：不是单个初始化/归一化 bug，而是当前 v2 的「稀疏活跃块 + flow + decoder」这条训练通路没有把 next-token 梯度有效传进主块/编码器（日志里 bank/E 梯度长期远小于 out_a/dec_a，输出跨上下文几乎不变）。
下一步建议：先做 **v2-lite 隔离实验**（密集块、直接 token 输出/简单 decoder），确认能超过 bigram 后，再逐项加回
稀疏活跃、flow、记忆、扰动场——每加一项都用这套逐 step 日志验证。

## Round 22：v2-lite 隔离实验（成功让模型开始学）

结构：密集块（k=8 全活跃）、无 flow、无记忆、simple last-token decoder、**直接 last-token 嵌入读出**、
全词表 CE、d=256/depth2（28.5M）、batch8、lr1e-3、8-bit Adam、bf16。
数据：**完整 zhwiki 用自训 BPE 16k tokenize → 520,588,287 tokens**（2.08GB）。

结果（20,000 步，~11 分钟）：
- 前 4k 步 held decode 5.86%，20k 步 held **5.47%**、train **5.08%**；
- 对比 smoke 语料 v2 完整结构 10k 步 held 1.56% → **v2-lite 确实开始泛化**；
- loss 持续下降，`cos_a` 从 0 升到 ~0.15；主块梯度 bank 从 1e-4 升到 0.2–0.5；
- 但 20k 步仍低于 bigram baseline（smoke 上 train 16%/held 9%），还需更长训练。

关键：**先砍掉 flow/记忆/扰动场/稀疏选择，用密集块+直接读出+CE**，模型才学得动。
下一步：v2-lite 继续跑 100k 步看 held 能否 >10%；然后逐项加回 flow → 记忆 → 稀疏活跃 → 扰动场，
每加一项用逐 step 日志验收。

## Round 23：v2-lite 100k 未达标 + 关键评估口径修正

- v2-lite（密集/无 flow/无记忆/simple decoder/CE）在完整 520M token 上继续到 ~50k 总步：
  held decode 一直在 **5.1–5.9%** 平台；100k 长跑中止，未出现 >10%。
- 发现评估口径问题：**m_out=8 的非自回归输出**中，位置 1..7 无法看到前一个目标 token，
  固定上下文下它们只能靠上下文硬猜，平均 held decode 被稀释；bigram baseline（teacher forcing）不可直接比较。
- 改跑单 token（n_out=1）标准 next-token：
  - v2-lite 单 token：held 6.25%、train 3–8%，仍低于 bigram（held ~9% / train ~16%）；
  - 纯 last-token 线性 CE：train 9.4%、held 6.25%（5k 步），说明**能学但只到 bigram 附近且噪声大**；
  - last+mean 混合上下文：held 6.25%，无突破。
- 结论：当前瓶颈是**训练采样方差大 + 模型对上下文利用弱 + 监督被非 AR 多位置稀释**，不是某个单点 bug。
- 下一步（未启动）：改成 AR/teacher-forcing 训练（每个位置用真实前文）、加大 batch/降低 lr/加 LR 调度，
  先把单 token held decode 稳定推到 >10%，再逐项加回 flow → 记忆 → 稀疏活跃 → 扰动场。
